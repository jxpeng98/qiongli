## Release Notes / 发布范围

- Public full-text reading through `qiongli_literature_read_fulltext`, with
  explicit provenance and bounded extraction. Lite exposes 15 tools and Full
  exposes 33. Public HTTPS retrieval retains destination and redirect checks;
  private libraries, signed access and paywall bypass are outside this release.
- Reviewed stage summaries, paper-note creation/append and structured source
  packets use the existing capture, preview, approval and revision/CAS owners.
  They preserve source hashes, history and existing user text. Saving a source
  packet does not implement retrieval-list persistence or establish a complete
  PDF, source identity, license or independent research acceptance.
- Focused paper-reading, writing, synthesis, evidence verification and discipline
  guidance. Codex remains the reference Host; Host adapters keep the user's
  configured models. This release does not add a new retrieval engine, Graph
  store, permanent Agent or broad cross-Host acceptance claim.
- Linux ARM64 joins native CLI archives, PyPI wheels, the combined npm package
  and native Marketplace Plugin archives. This fixes Ubuntu ARM64 silently
  selecting the older universal Python 1.x package when no compatible 2.x wheel
  existed. Existing language selection and 22 workflow entries remain available.
- Concurrent update-state reads wait for an active writer before treating its
  temporary files as recovery evidence. Interrupted transactions remain blocked;
  read-only checks preserve existing files and do not create configuration roots.

## Compatibility and channels / 兼容性与渠道

| Binary platform | Target | Minimum distribution baseline |
|---|---|---|
| macOS ARM64 | `aarch64-apple-darwin` | macOS 11+ |
| Linux x64 | `x86_64-unknown-linux-gnu` | glibc 2.35+ |
| Linux ARM64 | `aarch64-unknown-linux-gnu` | glibc 2.35+; includes Ubuntu 24.04 aarch64 |
| Windows x64 | `x86_64-pc-windows-msvc` | Native Windows x64 |

Python 3.9+ is required for pip, Node 18+ for npm, and Rust 1.97+ for Cargo.
Release qualification uses Rust **1.97.0**, Python 3.12 and Node 24. Binary
packages do not cover Intel macOS, Windows ARM64, 32-bit systems or musl Linux.
Cargo is a source build; it does not extend the qualified binary-platform list.
Desktop installers and external Marketplace catalog promotion remain separate.

Planned stable identities: GitHub `v2.2.0`, npm `qiongli@2.2.0` on `latest`,
PyPI/Cargo `qiongli` version `2.2.0`, and stable Plugin identity `qiongli`.
Historical tags, packages and receipts remain immutable. Choose one CLI channel
after publication:

```sh
npm install --global qiongli@2.2.0
python -m pip install --upgrade "qiongli==2.2.0"
cargo install qiongli --version 2.2.0 --locked
```

An explicit version prevents pip from silently falling back to 1.x. The registry
release must contain four wheels and one combined four-target npm package,
alongside four CLI archives and both Plugin families for every target. A
schema-2 release packet requires all four targets; historical packets through
2.1.1 retain their older reader. Source archives are not executable packages.

## Data preservation and rollback / 数据保留与回退

Package replacement must preserve research projects, captured sources, notes,
receipts, Host profiles, selected models and prior installation caches. Existing
research writes still need preview, explicit approval and current source/revision
checks; installation grants no research-write permission.

The new reader retains old receipts, but older binaries reject receipts carrying
the new saved-artifact types. Reinstalling 2.1.1 therefore does **not** provide a
general data downgrade after using these features. Keep a backup before upgrade;
retain the new CLI for projects with new receipts, or restore a separate
pre-upgrade copy for the older CLI. Never delete or rewrite receipts to make an
older reader accept a project. Re-export/re-enable the matching Plugin when
changing the CLI version; DSH uses its own package manager and keeps profiles.
The retained [rollback guide](rollback.md) does not override these native receipt
constraints.

## Validation Evidence / 验证范围

Development checks and earlier research observations are recorded in the current
plan. They are not evidence that these 2.2.0 registry artifacts are downloadable
or that the same frozen commit passes on every platform.

Readiness still requires the complete candidate's CLI/MCP checks, actual
CLI/Plugin/npm/PyPI/Cargo archives, isolated clean installs, old-version upgrade
and data-preservation checks, then target-native macOS ARM64, Windows x64,
Linux x64 and Linux ARM64 build/install receipts for the **same commit**.
Earlier 2.1.1 packages and the previous macOS observations cannot substitute for
that qualification. General academic accuracy, all disciplines and all Agent
combinations are outside the release gate.

## Publish Steps / 发布条件

1. Resolve release-relevant validation failures using the pinned toolchain and
   record the exact candidate commit in the plan. Keep deferred validation debt
   visible; do not remove negative permission, integrity or data-loss checks.
2. Run the existing CLI release owner and hosted distribution/Cargo checks
   without publishing; bind all artifacts and installation receipts to that
   frozen source. Any source change needs new artifact qualification.
3. Obtain a separate named publication decision for the verified bytes/channels.
   Only then integrate the authorized stable source into `main`, create its
   immutable tag and use the existing release automation. A branch push does
   not authorize tags, GitHub Releases or package uploads.
4. After authorized publication, independently download and install the public
   GitHub, npm, PyPI and Cargo artifacts. Announcement is a separate decision.

This preparation covers source synchronization and non-publishing qualification. No release, tag,
registry upload, external catalog promotion or announcement has been performed.
