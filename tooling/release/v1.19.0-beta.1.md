# qiongli `v1.19.0-beta.1` Release Notes

Date: 2026-07-11
Stage: Beta

## Highlights

- Prepared the final planned feature-bearing beta of the Python-led 1.x line
  and the reference boundary for the Rust-native 2.x migration.
- Completed the Stage 1 provider-configuration and literature-planning contract
  batches across Python Full, Rust Lite, and the legacy Node MCPB.
- Closed the Windows ACL, reparse-point, fail-closed configuration, and
  release-artifact acceptance gates on dedicated Windows runners.
- Advanced the Rust Lite MCP and Literature MCPB components to
  `0.2.0-beta.3` while preserving honest product/component version identities.
- Froze the 2.x migration plan without starting native 2.x implementation on
  `dev`.

## Final 1.x Scope

`v1.19.0-beta.1` is the final planned feature-bearing beta of the Python-led
1.x line and the reference behavior boundary for the Rust-native 2.x migration.
It contains no 2.x native-platform implementation.

This release does not claim that every 1.x surface is independent of language
runtimes. The Full CLI remains Python-backed, and the npm/npx path remains a
Node asset manager. Only matching-target plugin payloads that bundle the Rust
Lite executable are dependency-free at runtime. A zero-language-runtime Full
platform, native orchestrator, and native agent runtime remain 2.x objectives.

After post-release acceptance, `release/1.x-python` becomes the compatibility
oracle and critical-fix line. Normal 1.x feature development stops with this
beta.

## Behavior And Security Closure

- Added typed Capability Contract v2 records for `qiongli_config_status`,
  `qiongli_save_provider_config`, `qiongli_configure_provider`,
  `qiongli_literature_status`, `qiongli_search_plan`, and
  `qiongli_literature_export_evidence`; retained
  `qiongli_open_config_wizard` as a compatibility alias.
- Aligned provider activation, configuration status, bounded search planning,
  evidence export, semantic errors, redaction, and compatibility output across
  Full and Lite profiles.
- When every provider is disabled, Full and Rust Lite return explicit
  `strategy_only` / `no_active_providers` diagnostics without issuing provider
  requests.
- Disabled providers and credentials are excluded from search scheduling and
  external adapter environments.
- Malformed, unsupported, or unsafe shared configuration fails closed without
  overwriting the original bytes.
- Node configuration handling validates version and shape, rejects unsafe
  links and targets, uses same-directory atomic replacement on supported
  systems, tightens POSIX permissions, and redacts paths and secrets.
- Rust Windows writes create and verify a protected, current-user-only DACL
  before credentials are written and preserve it through replacement.
- Search-plan output retains canonical `from_year` / `to_year` fields and the
  deprecated `fromYear` / `toYear` aliases for the declared compatibility
  window.

## Contract And Governance Status

Capability Contract v2 remains `2.0.0-preview.3` with status `pilot`. Coverage
is exactly `6/23` canonical tools and `7/24` public names. This release does not
claim Contract v2 completeness; the remaining capability migration belongs to
the 2.x program.

AC1 academic analysis-code governance and RC1 repository source-code governance
are designed and scheduled in the roadmap, but neither is an enforced release
gate in this beta. AC1 still requires its canonical `AAC-*` contract, Stage I
integration, validator, semantic I8 review, and Q4 enforcement. RC1 still
requires its repository-only `RSC-*` contract, owned debt baseline,
changed-file validator, and release-preflight integration. Existing format,
test, security, and repository-boundary checks must not be presented as
complete AC1 or RC1 enforcement.

## Known Limitations And Accepted Decisions

1. **Owner-approved A1 limitation 1:** the dependency-free legacy Node MCPB
   cannot create a verifiable user-only Windows DACL. Its Windows save and
   wizard paths fail closed before creating or replacing shared configuration.
   Use Rust Lite for Windows configuration writes; Node remains read-only for
   that file.
2. **Owner-approved A1 limitation 3:** Rust Windows paths do not yet opt into
   extended-length `\\?\` handling. An unusually deep configuration path may
   fail closed without writing or disclosing credentials. Extended-length
   support is deferred to 2.x.
3. **A1 item 2 technically closed:** the dedicated Windows job executed native
   ACL tests, full Rust tests, clippy, Node fail-closed tests, and built-artifact
   stdio/DACL acceptance successfully.
4. **A1 item 4 technically closed:** the Windows runner created a real junction
   and verified that the Node read path rejected it without touching the target;
   POSIX symlink and cross-platform identity cases also passed.

The release owner approved limitations 1 and 3 and accepted the technical
closure of item 4 at `2026-07-11T00:02:51Z`. That decision is anchored to the
A1 evidence above. Final release acceptance remains bound to the actual tag and
post-release receipt.

## Maintenance And Rollback

After acceptance, `release/1.x-python` is critical-fix-only. Critical security
or release-breakage corrections require an explicit exception and a matching
Rust-side correction where applicable. The planned 1.x support window ends
90 days after Qiongli 2 stable unless a later support decision replaces this
policy.

The parameterized rollback runbook in `tooling/release/rollback.md` separates
an unpublished local-tag abort from an immutable public-release withdrawal. It
uses PyPI yank, npm version deprecation plus `next` fallback, a retained Git
tag, a branch revert commit, isolated downgrade validation, and a new forward
fix version.
