## Decision

The implementation-head Alpha.1 candidate completed the real Codex and Claude
Code lifecycle in separate fresh homes and client configuration roots. Both
clients installed and cached the candidate-materialized plugin source, the
cached receipt matched the candidate source receipt, the cached native binary
served all 12 Lite MCP tools with an empty runtime `PATH`, and client plus
Qiongli removal left the plugin absent.

This is not a publication receipt. The candidate used memory-only ephemeral
test keys, records `publication_allowed: false`, and covers only the current
macOS aarch64 portable target. Production signing, final accepted-source
regeneration, displayed-window gates, cross-platform clean-machine acceptance,
and explicit maintainer publication authorization remain unresolved.

## Isolation Boundary

- The candidate was assembled outside the checkout from a clean implementation
  head and embedded that exact source object ID.
- Codex and Claude Code used separate fresh homes and client configuration
  roots. XDG config, cache, and data roots were redirected into the same
  isolated homes.
- Actual client executable paths were resolved before the run; version-manager
  shims were not supplied to the acceptance executable.
- The Plugin Creator validator ran through an explicit Python 3.12 interpreter
  with PyYAML 6.0.3. This was an external development-only validation input;
  neither Python nor the validator was copied into or launched by Qiongli.
- Candidate source, client cache, MCP, client removal, candidate verification,
  candidate removal, and absence checks operated only on isolated state.
- Evidence output contains client versions, booleans, counts, and digests; it
  contains no private filesystem path or signing private material.
