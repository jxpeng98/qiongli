# Qiongli 2.0.0-alpha.1 Release Runbook

Status: R3P-A through R3P-D repository implementation complete; first protected
promotion/authorization run, offline signing, and publication pending

Community Alpha targets: macOS arm64, Windows x86_64, Linux x86_64

The first distribution is an explicitly labelled, zero-cost Community Alpha.
Publication remains blocked until R3P promotes one exact-head three-platform
candidate, completes target-native acceptance and the Community Alpha ledger,
and records explicit maintainer authorization. Existing CI artifacts remain
non-publishing evidence.

## Distribution Lanes

The authoritative decision is
`docs/superpowers/specs/2026-07-17-qiongli-community-alpha-distribution-note.md`.

| Lane | macOS | Windows | Linux | Eligible release |
|---|---|---|---|---|
| `community-alpha` | ad-hoc signed, not notarized | unsigned portable ZIP | AppImage, optionally GPG signed | prerelease only |
| `production` | Developer ID signed and notarized | trusted Authenticode and timestamp | signed release metadata/AppImage | later Beta/Stable hardening |

Both lanes require Qiongli's detached Ed25519 release/update signatures,
target identity, SHA-256 inventory, SBOM, provenance, and exact-set approval.
The free lane waives only paid operating-system publisher trust.

Community Alpha release notes and download surfaces must state that macOS uses
the per-app **Open Anyway** flow, Windows may warn or be blocked by SmartScreen,
Smart App Control, antivirus, or enterprise policy, and Linux requires the
facilities supported by the advertised AppImage. They must not tell users to
disable global security controls or import a self-signed Windows root.

## Community Alpha Implementation Gates

Before this runbook may publish the free lane:

- consume the implemented closed `community-alpha` policy/release-set schema
  and exact protected-environment authorization capability in the finalizer;
- promote fresh macOS ad-hoc DMG/ZIP, Windows portable ZIP, and Linux AppImage
  outputs from one exact clean source instead of uploading raw CI artifacts;
- bind all public assets into the existing Ed25519 authority, sorted checksums,
  CycloneDX SBOM, SLSA provenance, and Community Alpha receipt;
- pass target-native packaged startup acceptance on all three advertised OSes;
- review English and Chinese installation warnings; and
- consume explicit exact-release-set maintainer authorization before creating
  a tag, GitHub Pre-release, or preview update entry.

R3P-A now provides the machine boundary for the first and last items:

- `NativeDistributionPolicyV1` closes class, target trust, labels, warnings,
  Stable eligibility, and raw-CI non-publishability;
- `NativeDistributionReleaseSetV1` requires the exact three target policies,
  one version, one source revision, and one external release-set digest;
- `NativePublicationAuthorizationV1` is strict, bounded, canonical, and valid
  only for an exact GitHub protected Environment/run/actor/time context; and
- only `VerifiedNativeDistributionReleaseSet` represents successful policy-set
  and authorization consumption. It performs no tag, upload, endpoint, or
  update-stream mutation.

The actual promoted assets and signed evidence are intentionally deferred to
the first execution of R3P-B and then R3P-C. The R3P-D publishing workflow must
derive trusted comparison values from GitHub runtime context; the authorization
JSON alone is not proof of protected-environment approval.

R3P-B now provides `.github/workflows/native-community-alpha-promotion.yml` and
the Rust `native_community_alpha_promotion` example. The workflow runs on a
qualifying `2.x` push and retains a manual entry point for when the workflow is
available from the default branch. It is read-only, requires the requested
commit to equal current remote `2.x` HEAD, rebuilds all targets in the same run,
and emits only a three-target
`publication_allowed: false` candidate. It cannot tag, publish a GitHub Release,
or mutate update metadata. Run it only after this implementation is merged;
the workflow has not yet produced the first real candidate.

R3P-C and the R3P-D authorization boundary now provide:

- a checked-in public Alpha release authority embedded into every promoted
  executable while both private Ed25519 keys remain outside GitHub and the
  repository;
- `native_community_alpha_release`, which re-verifies the exact candidate and
  target-promotion receipts, emits sorted SHA-256 checksums, CycloneDX 1.6,
  SLSA provenance, bilingual release notes, and a signed integrity record;
- a `community-alpha-publication` GitHub Environment restricted to `2.x` and a
  required maintainer review; and
- a read-only post-promotion authorization job. It emits a short-lived exact-set
  authorization artifact but has no private key and no `contents: write`
  permission.

The final signing and `gh release` mutation run from the maintainer machine.
This is deliberate: GitHub never receives the private release key.

## Community Alpha Offline Signing And Publication

After the exact `2.x` workflow run passes and its protected Environment is
approved, use a clean checkout at the same source commit:

```bash
export RUN_ID="github-actions-run-id"
export SOURCE_COMMIT="exact-40-character-2.x-head"
export RELEASE_ROOT="/absolute/private/qiongli-alpha1-release"
export CANDIDATE_ROOT="/absolute/private/qiongli-alpha1-candidate"
export AUTHORIZATION_ROOT="/absolute/private/qiongli-alpha1-authorization"

gh run download "$RUN_ID" \
  --repo jxpeng98/qiongli \
  --name "qiongli-community-alpha-candidate-$SOURCE_COMMIT" \
  --dir "$CANDIDATE_ROOT"
gh run download "$RUN_ID" \
  --repo jxpeng98/qiongli \
  --name "qiongli-community-alpha-authorization-$SOURCE_COMMIT" \
  --dir "$AUTHORIZATION_ROOT"

export QIONGLI_NATIVE_SOURCE_COMMIT="$SOURCE_COMMIT"
export QIONGLI_NATIVE_RELEASE_AUTHORITY_FILE="$PWD/packages/qiongli-native/release/qiongli-native-release-authority.json"
IFS= read -r -s QIONGLI_ALPHA_RELEASE_PRIVATE_KEY_HEX \
  < "/secure/offline/qiongli-alpha-release.key.hex"
export QIONGLI_ALPHA_RELEASE_PRIVATE_KEY_HEX

cargo run \
  --manifest-path packages/qiongli-native/Cargo.toml \
  --package qiongli \
  --example native_community_alpha_release \
  --release --locked -- \
  prepare \
  --candidate "$CANDIDATE_ROOT" \
  --authority "$QIONGLI_NATIVE_RELEASE_AUTHORITY_FILE" \
  --cargo-lock "$PWD/packages/qiongli-native/Cargo.lock" \
  --output "$RELEASE_ROOT"

cargo run \
  --manifest-path packages/qiongli-native/Cargo.toml \
  --package qiongli \
  --example native_community_alpha_release \
  --release --locked -- \
  authorize \
  --release-dir "$RELEASE_ROOT" \
  --authorization-file "$AUTHORIZATION_ROOT/qiongli-community-alpha-publication-authorization.json" \
  --repository "jxpeng98/qiongli" \
  --environment "community-alpha-publication" \
  --workflow-run-url "https://github.com/jxpeng98/qiongli/actions/runs/$RUN_ID" \
  --actor "maintainer-login-from-the-run" \
  --verified-at-unix "$(date -u +%s)"

cargo run \
  --manifest-path packages/qiongli-native/Cargo.toml \
  --package qiongli \
  --example native_community_alpha_release \
  --release --locked -- \
  verify --release-dir "$RELEASE_ROOT" --require-authorization
```

Unset the private-key variable immediately after signing. Create a draft
pre-release, verify its exact asset inventory, and only then make it public:

```bash

gh release create "v2.0.0-alpha.1" "$RELEASE_ROOT"/* \
  --repo jxpeng98/qiongli \
  --target "$SOURCE_COMMIT" \
  --draft \
  --prerelease \
  --title "Qiongli 2.0.0-alpha.1 Community Alpha" \
  --notes-file "$RELEASE_ROOT/qiongli-2.0.0-alpha.1-community-alpha.release-notes.md"
gh release view "v2.0.0-alpha.1" \
  --repo jxpeng98/qiongli \
  --json tagName,targetCommitish,isDraft,isPrerelease,assets,url
gh release edit "v2.0.0-alpha.1" \
  --repo jxpeng98/qiongli \
  --draft=false \
  --prerelease
```

Until the exact-head promotion and protected authorization execute and pass,

## Production-Signed Security Boundary

The repository and Qiongli product never receive production private keys.

- macOS code signing uses an existing Developer ID identity and an existing
  `notarytool` Keychain profile.
- Update signing uses a canonical public authority document plus detached
  Ed25519 signatures produced by an external signer.
- The metadata tool accepts only public evidence, public key identifiers, and
  signature files containing exactly 128 lowercase hexadecimal characters
  with an optional final line feed.
- The external signer must sign the bytes represented by each
  `signing_preimage_hex` field, not the ASCII hexadecimal text.
- Every repository-produced receipt keeps `publication_allowed: false`.

## Production-Signed Required Inputs

- one exact-head unsigned macOS package directory from Native CI;
- the package source commit and package SHA-256;
- a canonical Alpha release-authority JSON file with separate release and
  launch-grant public keys;
- the selected release generation and key identifiers;
- production Developer ID, Team ID, and notarization access already configured
  on the maintainer machine;
- an external signer capable of signing the two launch-grant preimages and the
  later update-manifest preimage.

All paths passed below must be absolute. Every output path must not exist.

## 2. Prepare Launch-Grant Signing Preimages

Choose a validity interval that has not expired and a generation authorized by
both public key roles.

```bash
cargo run \
  --manifest-path packages/qiongli-native/Cargo.toml \
  --package qiongli \
  --example native_alpha1_update_metadata \
  --locked -- \
  prepare-grants \
  --signed-artifact-dir "/absolute/qiongli-alpha1-signed" \
  --authority "/absolute/qiongli-native-release-authority.json" \
  --generation "$GENERATION" \
  --published-at-unix "$PUBLISHED_AT_UNIX" \
  --not-before-unix "$NOT_BEFORE_UNIX" \
  --expires-at-unix "$EXPIRES_AT_UNIX" \
  --release-key-id "$RELEASE_KEY_ID" \
  --launch-key-id "$LAUNCH_KEY_ID" \
  --output "/absolute/qiongli-alpha1-grant-request.json"
```

Send only the two decoded `signing_preimage_hex` byte sequences to the external
launch-grant signer. Return the detached signatures as:

- `/absolute/qiongli-alpha1-codex.sig`;
- `/absolute/qiongli-alpha1-claude.sig`.

## 6. Record Final Acceptance Gates

Create exactly these seven receipt files in one flat evidence directory:

- `finder-clean-machine.receipt.json`;
- `packaged-ui.receipt.json`;
- `real-clients.receipt.json`;
- `production-update.receipt.json`;
- `rollback.receipt.json`;
- `accessibility.receipt.json`;
- `exact-head-ci.receipt.json`.

Each receipt uses this schema. `gate_id` must match its filename, every check
must be `true`, and every attachment must be a regular file in the same
directory with the exact recorded size and SHA-256:

```json
{
  "schema_version": 1,
  "record_type": "qiongli-alpha1-publication-gate",
  "gate_id": "finder-clean-machine",
  "status": "passed",
  "publication_allowed": false,
  "source_commit": "40-or-64-character-lowercase-object-id",
  "release_set_sha256": "supply-chain-receipt-release-set-sha256",
  "observed_at": "2026-07-16T12:00:00Z",
  "actor": "maintainer-or-ci-identity",
  "environment": "macos-clean-machine-description",
  "checks": {
    "finder_launch": true,
    "empty_path_startup": true
  },
  "attachments": [
    {
      "file": "finder-clean-machine.log",
      "size_bytes": 1234,
      "sha256": "64-lowercase-hex-characters"
    }
  ]
}
```

The gate receipt is an evidence assertion, not a substitute for running the
named journey. Screenshots, logs, CI exports, and other attachments must not
contain credentials or private signing material.

```bash
cargo run \

  --example native_alpha1_release_evidence \
  --locked -- \
```

Finalization fails closed for preflight evidence, a mismatched source or
release-set digest, a missing/false gate, unbound attachment, unexpected file,
or modified checksum/SBOM/provenance record. Success writes the canonical
ledger and its SHA-256 sidecar, but the ledger still says
`publication_allowed: false`. Explicit maintainer authorization remains
required before any release mutation.
